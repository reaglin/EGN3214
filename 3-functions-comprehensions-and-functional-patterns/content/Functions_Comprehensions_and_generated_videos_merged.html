Defining Functions

Introduction

A function is a named block of code that you define once and reuse whenever you need it. In Python, you create one with the def statement: you give the function a name, list any parameters in parentheses, and indent the body beneath the colon. When the function finishes, a return statement can hand a value back to the code that called it — and if you omit return, Python quietly returns None. Calling the function by name, with parentheses and any required arguments, is what actually runs that code.

This matters because almost everything that follows in the course is built on functions. Parameter styles, scope rules, recursion, and the functional patterns later in this module all assume you are comfortable with the basic def/return/call cycle. Good habits start here too: descriptive names in lowercase_with_underscores, and a docstring — a triple-quoted string on the first line of the body — that explains what the function does, what it expects, and what it gives back.

As you watch, keep three questions in mind. First, what is the difference between a function that returns a value and one that only prints something — can you use the result in an expression afterward? Second, where does execution go when a return runs, and what happens to any code after it? Third, what does the function need from the caller, and what does the caller get back? Try pausing and predicting the output before the narrator reveals it.

Parameters and Arguments

Introduction

When you define a function, the names listed in the parentheses of the def line are its parameters. When you call that function, the values you supply are its arguments. Keeping those two words straight makes it far easier to read error messages, documentation, and your own code, so this topic starts there and then builds outward to the different ways arguments can be matched to parameters.

Python gives you several options. Positional arguments are matched in order, left to right, so the order you write them matters. Keyword arguments are matched by name, which makes calls more readable and lets you skip the order entirely. Default parameter values let you declare a fallback in the function definition so callers can leave some arguments out, which is how most real-world library functions offer optional behavior.

As you watch these videos, pay attention to three things: the exact rule for where positional arguments must appear relative to keyword arguments, what happens when you pass too few or too many arguments, and how a default value changes which arguments are required. Try retyping each example in your own editor and then deliberately break it — swap the order, misspell a keyword, omit a required argument — so you learn to recognize the resulting TypeError messages.

Scope and Variable Visibility

Introduction

Every time Python encounters a variable name, it has to decide which value that name refers to. The answer depends on where the name is used. Python searches for names in a fixed order known as the LEGB rule: Local (inside the current function), Enclosing (inside any outer function that wraps it), Global (at the top level of the module), and finally Built-in (names like len and print that Python provides automatically). The first match wins, and if no match is found you get a NameError.

Scope matters in this course because you are now writing functions, and functions are the main way Python creates new scopes. Assigning to a name inside a function creates a local variable by default, even if a variable with the same name already exists outside the function. When you genuinely need a function to change a variable that lives elsewhere, Python requires you to say so explicitly with the global keyword (for module-level names) or the nonlocal keyword (for names in an enclosing function). Understanding this prevents a whole category of confusing bugs, such as a function that seems to update a counter but leaves the original unchanged, or an UnboundLocalError on a name you thought was global.

As you watch, keep three questions in mind for every example: where is this name first assigned, which scope does Python search first, and does this code read a variable or rebind it? Try predicting the output before the narrator reveals it, then pause and check. Pay particular attention to the difference between mutating an object (such as appending to a list) and reassigning a name, since only the latter triggers the need for global or nonlocal.

Recursion

Introduction

Recursion is a problem-solving technique in which a function calls itself on a smaller version of the same problem. Instead of writing a loop that repeats work, you describe the problem in terms of itself: a factorial of n is n times the factorial of n-1, the nth Fibonacci number is the sum of the two before it, and so on. Every correct recursive function needs two parts: a base case that stops the chain of calls and returns a direct answer, and a recursive case that moves the input closer to that base case.

This topic matters in EGN3214 because recursion is a natural fit for problems with nested or self-similar structure, and because writing it forces you to think carefully about what a function returns and how parameters change between calls. It also connects to how Python actually runs your code: each call occupies a frame on the call stack, so recursion that never reaches a base case, or that goes too deep, raises a RecursionError rather than running forever.

As you watch, keep three questions in mind for every example: What is the base case? How does the recursive case shrink the input? What would happen if the base case were missing or wrong? It is also worth noting where the videos compare recursion to an iterative loop, since in Python an equivalent loop is often faster and uses less memory even when recursion reads more clearly.

Comprehensions

Introduction

A comprehension is a compact way to build a new collection from an existing iterable. Instead of creating an empty list, writing a for loop, and calling append on each pass, you express the whole transformation in a single line: the expression you want to produce, the loop that supplies the values, and an optional condition that filters which values are kept. Python supports this pattern for lists, dictionaries, and sets, and the syntax is nearly identical in each case — only the brackets and the shape of the output expression change.

This matters in EGN3214 because engineering data work is mostly transformation: converting units across a list of measurements, pulling the sensor readings above a threshold, building a lookup table from names to values, or collecting the unique materials in a parts list. Comprehensions make these operations short and readable, and they appear constantly in real Python code, so you need to be able to both write them and read someone else's. They also set up the next topic, where you compare comprehensions against lambda, map(), and filter().

As you watch, keep a mental template in view: output expression, then for variable in iterable, then optional if condition. Notice where the filter clause goes and how it differs from an if-else placed before the for. Pay attention to the dictionary form, which needs a key-value pair separated by a colon, and to nested comprehensions, where the order of the for clauses matches the order you would write them in a normal nested loop. If a comprehension ever becomes hard to read, that is a signal to write it back out as a loop.

Lambda Functions and Functional Patterns

Introduction

So far in this module you have written functions with def, given them names, and called them by those names. Python also lets you create small, unnamed functions on the fly using the lambda keyword. A lambda is limited to a single expression, and its value is the result of that expression, which makes it useful whenever a function is needed only briefly — most often as an argument passed to another function.

That pattern of passing functions as arguments is the heart of functional programming in Python. The built-ins map() and filter() each take a function plus an iterable: map() applies the function to every item and produces the transformed results, while filter() keeps only the items for which the function returns a truthy value. Combining them lets you transform and select in one pipeline. Because these tools return lazy iterators rather than lists, you will usually wrap them in list() or loop over them to see the results.

The practical question for this course is not whether you can write map() and filter(), but when you should. Comprehensions often express the same logic more readably, and a named def function is clearer than a complicated lambda. As you watch, pay attention to the syntax rules (what a lambda can and cannot contain), to how each video converts the result of map() or filter() into a visible list, and especially to any guidance on readability — that judgment is what you will be assessed on.
